# HANDOFF.md

**For: the person who inherits this repository.**

You do not need to understand all of it. You need to know **which five files
matter** and **where the bodies are buried**. Those are different skills. This
document is for the second one.

## 1. What this project is, in three sentences

> Coptic is the last stage of Ancient Egyptian, spoken liturgically in Coptic
> Orthodox churches every week and almost absent from the internet. This project
> puts a scholarly dictionary, 2.38 million words of annotated text with parse
> data, aligned human translations, a concordance, a starter course and
> flashcards into a fast static website that works offline and costs nothing to
> run.

If you can repeat that to someone else, you understand the project.

**Who made it:** Michael Helmy, project author and maintainer. See `AUTHORS.md`.

**Who made the *data*:** other people, and they matter more. The Coptic
Scriptorium maintainers lost their NEH funding in 2025 and are the actual authors
of the corpus this site depends on. See `GOVERNANCE.md` §Attribution and
`AUTHORS.md`.

## 2. Architecture at a glance

```
 sources                    STAGE A (weekly, GitHub Actions)        STAGE B (Cloudflare Pages)
 ─────────────────────      ──────────────────────────────         ───────────────────────
 CCL v1.2 TEI   ─┐
 CDO TEI        ─┤       parse/tt.py ─┐
 Kaikki JSONL   ─┼──▶   parse/*.py ──┼──▶ merge/entries.py ──▶ data/dist/** ──▶ Hugo ──▶ public/**
 UD CoNLL-U     ─┤       (raises on   │   (precedence rules)    (committed)       + Pagefind
 Coptic          ─┤        drift)     │   (attributions[])      shards, corpus     (seconds)
 Scriptorium _TT ─┘                  │                         tarball, CSV
                                     └──▶ validate/*  ──▶ ✅ or ❌ fail the PR
                                                                          + Worker index
                                                                             (1 pass)

                    GIT COMMITS ──▶ Cloudflare Pages (global CDN, $0)
                                        │
                                        └──▶ PWA service worker (24 MB runtime cache)

  GitHub Issues ◀───── ONE Cloudflare Worker ───── Suggestion form on the site
  (source of truth)      (contributions ONLY.          (no account required)
                          reading never calls it)
```

**The three-stage mental model: sources → bake → build → serve.** Stage A
(the bake) runs on a schedule and commits its output, because Cloudflare Pages
Free has a **20-minute build timeout** and the corpus will not fit through it.
Stage B (the build) must stay seconds.

### The one invariant that outranks everything

> **Nothing a reader does to read this site touches a runtime service.**
>
> The Worker handles contributions. Delete it and reading is unaffected. Keep
> this true and the project stays $0, works with JavaScript disabled, and cannot
> be taken down by an outage.

## 3. The five files that matter most

Everything else is replaceable. These five are not.

| # | File | Why |
|---|---|---|
| 1 | **`tools/collate.py`** | Coptic alphabetical order. Sorting by Unicode codepoint is **wrong** and looks fine to anyone who cannot read Coptic — the four Greek-borrowed letters ϣ ϩ ϭ ϯ would sort before ⲁ. Alphabet is name-resolved from Unicode, not hand-typed. **Do not edit the letter table without a linguist, and do not remove the collation test.** |
| 2 | **`tools/parse/tt.py`** | Parses the corpus. The `_TT` format is **not well-formed XML** — `ElementTree` fails on it. Any parser that raises instead of skipping is correct; a parser that "handles" malformed input by silently dropping verses will quietly corrupt the site. |
| 3 | **`tools/merge/entries.py`** | Merges CCL + CDO + Kaikki. **The precedence rules and the "never merge distinct senses" rule live here.** Read it before changing any merge behaviour. |
| 4 | **`tools/validate/*`** | The gates that stop bad data shipping: schema, licence, provenance, NC allowlist, corpus counts, collation. If you disable one of these to make a build pass, you have removed a safety net, not fixed a bug. |
| 5 | **The Cloudflare Pages build command** (Dashboard → Settings, or `build.sh`) | Hugo + one Pagefind pass + SW manifest. Touch this and search silently breaks. |

## 4. The five things that will break first

Ranked by likelihood × impact.

### 4.1 `_TT` format drift in Coptic Scriptorium

**Likelihood:** high, over years. **Impact:** high — silently wrong alignments.

They ship v6.4.0, the `<norm>` attributes change, your parser keeps running and
returns *plausible but wrong* data. **This is the worst failure mode on the
list** because nothing looks broken.

**What you will see:** `corpus_counts.py` fires in CI — verses or documents
dropped more than 2%. It will not fire for a subtle schema change that keeps the
counts plausible, so also run a diff on 20 random entries when you bump the pin.

**What to do:** `git checkout main && make -C tools parse` on the old pin, then
on the new one, then diff `data/dist/provenance/records.csv`. Read the changed
rows. If `<norm>` lost an attribute, update `tt.py` and **make the parser raise**
if that attribute is absent.

### 4.2 Kaikki schema change

**Likelihood:** moderate. **Impact:** low — Kaikki is a supplement (3,293 of
~11,500 entries).

They change the Wiktextract field names. `parse_kaikki.py` has a hard count gate
(expects > 2,500 records) that fails loudly. Update the field names; if it stops
being useful, delete it. **The site does not depend on it.**

### 4.3 Cloudflare Pages file-count creep

**Likelihood:** moderate. **Impact:** total — the deploy fails at 20,000 files.

Currently ~950. CI fails at 15,000. **The usual cause:** someone regenerates all
11.5K dictionary entries as HTML pages instead of using the shard reader, which
eats 58% of the budget on its own.

**What to do:** `find public -type f | wc -l`. If it is climbing, find what is
multiplying. Do **not** raise the CI ceiling to make it pass — that is how the
site becomes undeployable.

### 4.4 Licence challenge on a newly added source

**Likelihood:** moderate. **Impact:** severe — legal.

Someone claims a source is not properly licensed, or a "public domain" item
turns out not to be, or an NC source reached the dataset.

**What to do:** **do not argue.** See `RUNBOOK.md` §4. Take it down, log it in
`/licences/takedowns.md`, respond within 7 days, resolve or remove permanently.
The NC allowlist (v4 §9) failing closed means this should not happen — but check
whether the item was added to `ALLOWED_SOURCES` without a licence verdict.

### 4.5 Worker token expiry / revocation

**Likelihood:** moderate. **Impact:** low — contributions only.

The token gets revoked, expires, or the PAT owner leaves. `/api/health` returns
`ok: false`, or every submission 503s.

**What to do:** `npx wrangler secret put GITHUB_TOKEN` with a fresh PAT
(`issues:write`). **Reading is never affected** — confirm that first if someone
reports an outage, because they may be reporting something else entirely.

## 5. Bake, deploy, roll back

**Step 1 — fetch the corpus. A clean clone has no `sources/**/*.tt`.**
`sources/corpus/<slug>/*.tt` is **fetched, not vendored**: ~20 MB of Coptic source
that upstream can change, which is why `sources/` is in `.gitignore`. Needs the
pinned corpora release tarball once (~831 MB — see `RUNBOOK.md`).

```bash
.venv/bin/python tools/fetch/fetch_work.py --tarball /tmp/corpora.tarball.tar.gz
.venv/bin/python tools/fetch/fetch_work.py --check     # 9 works vs their pins
```

Do not skip this. `tools/build.py` **succeeds without it** and ships a site with
no corpus, so it fails at the point where the reader is already looking at a page
that should have verses on it.

```bash
# ── full bake, locally ────────────────────────────────────────────────
git clone https://github.com/Michaelhehelmy/coptic-reference && cd coptic-reference
make -C tools all          # fetch → parse → merge → emit → validate
                           # ~12 min on a laptop, ~2 GB RAM, no GPU

# ── just the pieces, while iterating ─────────────────────────────────
make -C tools parse        # sources/ → work/
make -C tools merge        # work/ → merged/
make -C tools emit         # merged/ → data/dist/
make -C tools validate     # the gates. Non-zero exit = do not commit.

# ── what changed? this is the review surface ──────────────────────────
git diff --stat data/dist
git diff data/dist/provenance/records.csv   # ← actually read this one
git diff data/dist/provenance/LICENSES.csv   # ← and this one

# ── build the site locally ───────────────────────────────────────────
hugo --gc --minify --baseURL http://localhost:1313
node tools/emit/pagefind_index.mjs     # ONE pass. not two.
npx serve public -l 3000
```

**Deploy — a push does not deploy (Rule 16).** The Cloudflare Pages project
is git-connected, but its builds have produced empty 404 deployments since
Session 15 (dashboard config, not fixable from the CLI): every push from
Sessions 15–22 changed the live site nothing while production decayed to
Session 15 content. The working path is a direct upload of the baked tree:

```bash
export WRANGLER_SEND_METRICS=false        # telemetry makes the deploy fail
npx wrangler pages deploy public --project-name coptic-reference --branch master
```

Then run `POST_DEPLOY_CHECKLIST.md` against **the deployment URL wrangler
prints** (the checklist targets it deliberately — the apex can serve
edge-cached HTML for days, and Session 24 measured it serving an empty
origin underneath that cache; the deployment hostname always reflects
the upload). Rebuild before deploying if code or content changed —
`wrangler` uploads `public/`, it does not run the bake. `git push` is
for history only; it is not a release step — and **the deploy must be
the last act**: a push after a deploy creates a fresh empty git
deployment that can take the production alias away from what you just
shipped (Session 24 D4). Cache invalidation and the purge API:
DEPLOY.md §6.

**Roll back:**

```bash
# site — revert, rebuild, deploy (~5 min; pushing alone does nothing)
git revert <sha> && make -C tools all && npx wrangler pages deploy public \
  --project-name coptic-reference --branch master

# one bake that went wrong — restore the last good data/dist
git checkout <last-good-sha> -- data/dist && git commit -m "revert data/dist" \
  && npx wrangler pages deploy public --project-name coptic-reference --branch master
```

**Force-push `data/dist` is almost never right.** If a bake produced bad data,
revert the commit. The only exception is when a bad bake corrupted something the
next bake cannot regenerate from the pinned sources — and since all sources are
pinned by SHA-256, that essentially never happens.

## 6. How to review a suggestion (Steward workflow)

You cannot approve anything. You can only get things to the right person. See
`GOVERNANCE.md` for the rights.

```bash
gh issue list --label suggestion --label status/new \
  --json number,title,labels,createdAt --limit 50
```

For each one, in order:

1. **Read it.** If it is unclear, ask one question and wait. Do not close it.
2. **Within 7 days**, apply exactly one:
   - `status/triaged` — you understand it, now it needs a decision
   - `status/duplicate` — link the original with `gh issue comment N --body "Duplicate of #X"` and close it *politely*
3. **Label the target:** `entry/<id>` · `work/<urn-short>` · `lesson/<slug>` · `site`
4. **Escalate:**
   - `kind/licence` → **same day**, add `reviewer/licence`
   - `kind/gloss` · `kind/parse` · `kind/translation` → add `reviewer/linguistic`
   - `kind/translation` **on a liturgical work** → also add `reviewer/theological`
5. **Set priority:** `priority/high` if it affects a widely-read entry or a
   licence; `priority/medium` normally; `priority/low` if cosmetic.
6. **Never** move something to `accepted`. That is the Maintainer's call after
   a Reviewer has responded.

```bash
gh issue edit 421 --add-label status/triaged,entry/C5047,reviewer/linguistic,priority/medium
gh issue comment 421 --body "Thank you — this is with a linguist now. Target: 30 days."
```

**Say thank you in every case, including declines.** A contributor who is told
*why* something was declined will come back. One who is silently closed will not.

## 7. Adding a data source

Full procedure: **`CONTRIBUTING_SOURCES.md`**. Four gates, all mandatory:

1. **Pin** — url, SHA-256, bytes, snapshot date, licence, DOI, citation in `tools/sources.lock`
2. **Licence verdict** — a real licence. `UNKNOWN` fails the build. "Open access" is not a licence
3. **Allowlist** — add to `ALLOWED_SOURCES` in `tools/validate/nc_guard.py`. This is fail-closed: nothing reaches the dataset without it
4. **Diff review** — `records.csv` and `LICENSES.csv` reviewed by a second person

**No source ships without a machine-readable licence verdict.** If you cannot
determine the licence, **link to the item — do not mirror it.**

## 8. What NOT to do

Each of these has a specific reason. Do not "improve" past them.

| Do not | Why |
|---|---|
| **Do not add AI or ML** | Runtime or build. The corpus already carries `pos`, `lemma`, `func`, `head` from `_TT`, so parsing needs no model. A model in the build is a reproducibility and licence liability |
| **Do not link GPL-licensed code into this tree** | `cs_ocr` (GPL-3.0) and the remnqymi pipeline (GPL-3.0) must stay behind a subprocess or be reimplemented against public data. This tree is Apache-2.0 |
| **Do not add an NC source to `data/dist/`** | CC BY-NC does not mix with CC BY-SA. NC material lives in `content/nc/` and `static/pdf/` only. `nc_guard.py` fails closed and CI enforces it |
| **Do not regenerate all 11.5K entries as HTML** | Eats 58% of the Cloudflare Pages file budget. Use the shard reader. Static pages are for the top 300, for SEO and no-JS |
| **Do not remove or weaken the `collation_hash` test** | Then the alphabet becomes an invisible implementation detail instead of a reviewable artifact |
| **Do not make the Worker load-bearing for reading** | It breaks the invariant, the $0 budget, and offline use |
| **Do not require an account to submit** | It is the single largest reason a diaspora community never contributes. `mailto:` and the Worker both stay account-free |
| **Do not add a database** | Not D1, not KV, not R2. Dedup is stateless. A datastore turns a $0 project into one with a bill |
| **Do not soften `decide_by`** | It is the difference between "maybe after a year" being a commitment and being a hope. CI enforces it |
| **Do not bump a `sources.lock` SHA without reading the diff** | A silent upstream change is how 11.5K entries change without anyone noticing |
| **Do not reference `site.Data` in a template, and keep `data/` to what a template could safely parse** | The moment any template touches `site.Data`, Hugo unmarshals EVERY file under `data/` — including `corpus.tar.gz` and any binary a pipeline drops there — and the build dies (E35). Emit static pages with `tools/emit/*` and copy them in `tools/build.py`; binaries live in `work/` |

## 8a. How to write a guard (Session 5)

Two rules, added after Session 4 shipped a corpus with no text in it and Session 5
found three guards that passed with the entire dictionary deleted. Both cost a full
session to learn, so they are rules now.

**Rule 1: A checker that generates the artefact it verifies is not a checker. If a
guard regenerates the file it checks, it will always pass. Guards must read from
disk, never write.**

`dialects_check.py` ran `tools/emit/dialects.py` and then compared the result to
the shards. It therefore compared a file it had just written against the data that
had just written it — always true. It passed a `dialects.json` with
`no_dialect_recorded: 0`, which is precisely the dishonesty Q4 exists to prevent.
Generating the artefact is a *build* step. Verifying it is a *check* step. If one
function does both, the check is theatre.

**Rule 2: A guard that measures a proxy for the thing will pass when the thing is
absent. At least one guard per artefact must measure the thing itself. Sizes,
counts, and stable fingerprints are proxies; they pass whether or not the artefact
is correct. Every guard should have a companion that measures the artefact
directly, or a written note in COVERAGE.md saying why it doesn't need one.**

The empty corpus passed everything for a whole session: the round trip (it looks up
by lemma), the occurrence counts (it counted lemmas), the file sizes (JSON keys
cost bytes whether or not the value is empty), and the fingerprints (they hashed
`meta.json`, which held counts). Every check was correct about what it measured.
Together they said the corpus was healthy while it was empty.

With the dictionary deleted, `nc_guard`, `licence_guard` and `dry_run --real` all
printed OK / PASS, because **zero entries is a perfectly valid dataset** to a loop
with no zero check. A proxy measures zero just as happily as it measures ten
thousand.

Three consequences that follow directly:

- **Zero is a failure, not a skip.** A guard that needs a dataset and finds none
  fails, unless it is explicitly told an empty tree is acceptable. Silence and
  success look identical in CI, so the guard has to say which it means. (Two
  guards still `SKIP` with exit 0 on an absent artefact — `corpus_text_guard` and
  `tarball_repro_check` — which COVERAGE.md records as an open item.)
- **Traversal lives in one place.** Rather than teaching five guards about gzip,
  `tools/shardio.py` resolves `.json` and `.json.gz` and *fails* if it finds no
  shards. Then a compressed shard cannot be missed, because no call site chooses
  how to read.
- **Read and write are symmetric.** A module that reads a format must also write
  it. `shardio` had a reader and no writer, so `corpus_refs.py` invented its own
  and wrote plain JSON into 23 files named `shard-NNN.json.gz` (S5-B2).

**Before you trust a new guard, break it.** Write the negative control first: make
the artefact wrong on purpose and confirm the guard exits non-zero. Four of the six
bugs found in Sessions 4 and 5 were found by that discipline, not by reading code
carefully. A guard with no demonstrated failure is an assumption.

`tools/validate/COVERAGE.md` is the map: for every guard, what it measures, what it
catches, **what it would pass silently**, and its companion. Consult it before
adding a guard, and update it when you add one.

**Rule 3. Every artefact write is verified by read-back. A write that reports
success is a claim; a read-back is evidence. Filesystems fail, NFS reorders,
containers unmount — none of them announce themselves. If the code can't
re-read what it wrote, the write did not happen.**

This is `tools/safeio.py::write_verified()`, and it is the ONLY way artefact
writes happen in this project: write to `path + ".tmp"`, `fsync`, `os.replace`,
then read the file back and compare. Any mismatch raises and the build stops.

Rule 3 exists because the alternative was already tried and it failed twice in
one session:

- `emit/cli.py` printed `LICENSES.csv 19 row(s)` on a write that had not landed.
- Then `is_file()` came back False for the file it was about to regenerate, so
  the "previous" licence map was empty and every `originators` / `reference` /
  `notes` value was replaced with a blank. The emitter still reported success.
  **A licence manifest that silently forgets where its sources came from is
  invariant 7 breaking in the most literal way available**, and no amount of
  correct code downstream can recover it.

I then misdiagnosed that as a broken filesystem, and "fixed" a machine that was
fine. The actual bug was a one-letter filename difference (`LICENCES.csv` vs
`LICENSES.csv`) that meant the generated manifest was never the file any guard
validated. Rule 3 would not have caught *that* either — which is why Rule 2's
companion guards read the artefact, and why `licence_guard` now reads the same
name the emitter writes.

Use it:

```python
import safeio
safeio.write_verified(dest, payload)              # bytes; compresses iff .gz
safeio.write_text_verified(dest, "text\n")        # text, utf-8
```

Never call `write_text` / `write_bytes` on a path under `data/dist/` or
`public/`. If you find yourself needing `os.replace` by hand, you want
`write_verified` instead.

**Rule 4. When something does not work, the first hypothesis is that the code is
wrong. Environment is last, with a reproducible mechanism.**

Session 6 cost a full session to learn this. A licence manifest was unreadable and
every test touching it failed. The evidence was genuinely confusing — `os.listdir`
listed the file while `stat`, `open` and `unlink` could not reach it — and the
cause was that I had written `LICENCES.csv` where every reader expected
`LICENSES.csv`. Two literals, one letter apart.

What made it expensive was not the confusion. It was that I reached for the
environment before I had looked at my own strings, and then I "fixed" a healthy
machine instead of reverting a two-character diff.

So, in order:

1. **Re-read the code you just wrote.** Especially string literals, paths and
   filenames. `grep -rn "LICENCES" tools/` and `grep -rn "LICENSES" tools/` side
   by side would have taken ten seconds.
2. **Reproduce it outside your framework.** A 7-line script doing the same
   `write` then `stat` distinguishes "my code is wrong" from "the machine is
   wrong" in under a minute. It passed 5/5, which should have ended the hunt
   immediately.
3. **Check whether a minimal reproducer fails in the framework too.** If your own
   test passes and the project's fails, the bug is in the project, not the world.
4. **Only then, the environment** — and with a *mechanism*, not a vibe. "This is
   NFS and `close()` may drop pending writes" is a mechanism. "This filesystem
   seems flaky" is not, and acting on it means `fsck`-ing a healthy disk.

Blaming the environment is cheap and unfalsifiable, which is exactly why it is
dangerous. Every environment excuse must come with the command that reproduces it
without your code in the way. If you cannot write that command, it is Rule 4 case
1.

**Rule 5. public/ is a build product; only the build writes to it.**

`public/` is deleted and recreated by `tools/build.py` on every build. A file
gets there by being emitted by a step that records it in
`BUILD-MANIFEST.json`, or by being copied from `static/`/`content/` by Hugo.

Never `cp` into `public/`. Session 8 is why: I hand-placed
`data/provenance/LICENSES.csv.gz` with `cp` — and that file **names the six
CC BY-NC sources it excludes**, so invariant 5 was broken by the one step in this
project with no gate in front of it. `nc_guard_public` caught it on the next run,
but only by luck of ordering. `cp` has no guard; the build does.

If you want a file published, add it to `static/` or `content/` so a generator
owns it. `tools/validate/public_provenance_guard.py` fails the build on any file
nobody can account for, which is the mechanism that makes this rule checkable
rather than aspirational.

**Rule 6. Tests never write to files they do not own.**

A test may write into its own `tmp_path`. It may not write into the repository.
The failure mode is specific and nasty: a test that writes `sources.lock` — or
`data/dist/**`, or any pinned artefact — leaves it subtly different, every later
test and every guard sees the mutated tree, and the damage is attributed to
whatever ran next.

`tools/tests/conftest.py` asserts that `tools/sources.lock` is **byte-identical at
session teardown**, so a test that touches it fails loudly at the end of the run
rather than silently corrupting the next one. This is the same discipline as
Rule 3 on the build side: a write that reports success is a claim, and a
read-back is evidence — here the read-back is at the end of the session.

Session 8 added the negative control that proves it works: a test that writes to
the lock, run deliberately, must fail at teardown.

**Rule 7. A component that exists and passes every guard but does nothing is a
shipped bug, not a success. Every artefact needs a behavioral test: not "does it
exist" but "does it do the thing it's for." A file that loads is not a file that
works.**

Session 10 found six of these in one session. Each passed provenance, passed the
completeness guard, built cleanly, and did nothing at all:

- `public/sw.js` — generated, 8 valid precache URLs, **never registered**
- `static/js/reader.js` — 211 lines, unit-tested, **no `#q`/`#results`/`#entry` on the page**
- `corpus_pages.py` — 6 routes emitted, **page-relative URLs → 404 on every page**
- `index.json.gz` — 154.7 KiB of search, **`reader.js` ignored `?q=`**, so every link dead-ended
- Pagefind index — built and passed, **skipped silently on stderr** when the binary was absent
- `sw_gen.mjs` precache list — validated, **but the footer never called `register()`**

The pattern, and the reason this rule exists: every one of these was checked by a
guard that measured a **proxy** for the thing that mattered. Provenance asks "is
this file accounted for", not "does it do its job". Existence asks "did the build
emit it", not "does it function". A proxy passes precisely when the artefact is
absent, useless, or unwired — which is the exact state these were in.

The test that catches this is not a structural assertion. It is one that drives
the component and asserts on the *effect*: register the worker and read the
cache; type into the box and assert the entry rendered; click the token and
assert the dictionary opened on the right lemma. Those fail when the thing is
broken. "File exists", "route 200s", "script tag present" — none of them fail
for any of the six.

`tools/tests/test_behaviors.py` holds six such tests, one per Session 10 bug, each
written so that reintroducing that bug fails the test. The negative demonstrations
are recorded in `COVERAGE.md`; they are the proof the tests are not vacuous.

**Rule 8. A test that passes on one sample has not tested the feature. Test with
at least two inputs that differ in a known way. If the sample you tested
happened to work for unrelated reasons, you have tested the sample, not the
feature.**

Session 11 is the evidence, and it is uncomfortable. Two separate mistakes, both
the same shape:

- **One input.** The corpus reader was verified against `sahidic_ruth` only —
  the one work of six whose verse refs happen to be unique. Five of six works
  rendered the wrong tokens, and every test passed, because the other five were
  never opened. A second input that differs in the *relevant* way (unique vs
  colliding refs) would have failed immediately.
- **One host.** Every test server in the project serves `.gz` **without**
  `Content-Encoding: gzip`. `reader.js` inflated every response unconditionally,
  which is correct only for that host. Cloudflare Pages sends the header, the
  browser inflates once, and the reader inflates again and throws — so the reader
  would have worked in all 295 tests and failed on the deploy target. A second
  input that differs in the relevant way (header present vs absent) would have
  failed in CI.

The pattern: each defect lived in a dimension where the project's single sample
was degenerate. Ruth was degenerate for refs; the local server is degenerate for
encoding. **A test must vary the property the code branches on**, not just repeat
the happy path.

Concretely, in this repo:

| Code branches on | Minimum test inputs |
|---|---|
| `Content-Encoding: gzip` present / absent | both, explicitly mocked |
| verse refs unique / colliding | at least one work of each |
| upstream source present / declared absent | both (3 of 9 works) |
| capital present / absent in a headword | both |
| `Mn`/`Me`/`Cf` mark present / absent | both |
| JS with a space in its path / without | both |

`tools/tests/test_fetch_json.py` exists because of the second row: it mocks both
encoding cases rather than inheriting whatever the local server happens to do.

**Rule 9. Test under deployed conditions, not development conditions. A test that
runs against a local dev server does not prove anything about the CDN. Where the
condition cannot be reproduced locally — CSP, headers, CDN behavior, TLS —
simulate it. A Playwright conftest that serves the emitted `_headers` is worth
more than a hundred local tests.**

Session 12 is the evidence, and the failure was silent and total.

The Playwright suite ran against `python3 -m http.server`, which sends **no
security headers at all**. The moment the conftest was changed to serve the real
`_headers` — the file the build actually emits — three Pagefind tests failed:

```
Error: Failed to load the Pagefind WASM:
CompileError: WebAssembly.instantiate(): Compiling or instantiating WebAssembly
module violates the following Content Security policy directive because
'unsafe-eval' is not an allowed source of script in "script-src 'self'"
```

Pagefind compiles WebAssembly in a worker. Under a development server there is no
CSP, so search worked in every test; under the policy Cloudflare would serve,
search returns nothing — on every page, for every reader, with no error message.
Not one of the ~300 tests would have caught it. The change that found it was four
lines in `tools/tests/playwright/conftest.py` reading the emitted `_headers`.

The general shape, which has now bitten three times:

| Condition | Dev server | Deployed | Caught by |
|---|---|---|---|
| `Content-Encoding: gzip` | absent | **present** | Rule 8: mock both |
| corpus ref uniqueness | Ruth only | 5 of 6 works broken | Rule 8: two inputs |
| CSP / WASM | none | **blocks search** | **Rule 9: serve the real headers** |

**Every "it works locally" claim in this project should be read as "it works
locally under conditions that are not the deployed ones."** Before believing one,
name the condition it depends on, and reproduce that condition — not a proxy for
it, and not nothing at all.

**Rule 10. A null result from a probe is not evidence until the probe has
produced a positive result on a case that should succeed. Before reporting "X
returns 0" or "Y doesn't work," run the probe against an input whose answer is
known to be non-null. If the probe cannot produce a positive result, it has not
been tested — it has been aimed.**

Session 13 nearly filed a false bug report because of this, and the near-miss is
more useful than the rule.

Checking the deployed site, `/dict/?q=ⲃ︦` returned **0 hits**. That is the
lemma that depends on `strip_chars` — a defect hunted across two sessions. The
evidence looked airtight: the URL came from the page, the site was live, the
response was a real 0.

It was the probe. The percent-encoding was hand-written:
`%E2%B3%83` is U+2CC3, not `ⲃ` U+2C83. Recomputing the encoding gave **297 hits**
locally and on the CDN.

The same mistake, twice in one session, with the same shape:

| Reported | Actually | Why |
|---|---|---|
| "`?q=ⲃ︦` returns 0 — U+FE26 broken in production" | 297 hits | my hand-written percent-encoding |
| "SW precache declares 10, tool reports 8" | 8 = 8 | my regex matched the *template* `PRECACHE = [`, not the emitted array |

In both cases a nearby value looked like a contradiction, and I was about to
report it. In both cases the probe had never produced a positive result, so it
had never been tested.

The discipline, stated so it can be followed:

1. **Calibrate first.** Run the probe against an input whose answer you know.
   `?q=ⲃ` (a bare headword) returned 297 while `?q=ⲃ︦` returned 0 — *that*
   asymmetry was the tell, and it should have stopped me immediately: two inputs
   that differ only by a combining mark, one working and one not, is a far more
   specific claim than "0 hits", and it was false.
2. **Let the code compute.** `urllib.parse.quote(q)`, `json.dumps`, a parser —
   never a hand-written literal. Every one of these failures was a literal that
   a function should have produced.
3. **A near-miss is a finding about the probe.** When a surprising null appears,
   the first hypothesis is the measurement, not the artefact.

This is the same shape as Rules 7, 8 and 9: each exists because something passed
or reported cleanly while doing nothing useful. A probe that reports 0 is a
component that does nothing, and Rule 7's remedy applies to it too.

**Rule 11. Every field whose schema type is object or array has exactly one
renderer, and every template calls it. A raw structured value in a template is
a bug that produces `[object Object]`, `undefined`, or a concatenated mess. If
two templates read the same structured field independently, one of them will be
wrong.**

Session 16 is the evidence. `static/js/reader.js` interpolated the schema's
`translit` object directly, while the Obsidian emitter read its keys one at a
time. One of the two could not be right: the reader printed
`[object Object]` for any nonempty transliteration. `static/js/translit.js`
now owns the field, and all renderers call `translitDisplay()`.

**Rule 12. Every file format in the pipeline has exactly one reader and one
writer. No call site opens a file directly. A file that exists in multiple
on-disk forms has exactly one reader that resolves all forms.**

Session 17 is the evidence, twice over. First the S5-B2 class: plain JSON
written into files named `.json.gz`. Then its mirror image in Session 17:
`tools/emit/cli.py` resolved the prior LICENSES manifest (possibly `.csv.gz`)
and opened the result as text, crashing the emit on gzip magic — resolving
the form and then ignoring the resolution. `tools/validate/reader_usage_guard.py`
enforces the rule: shard reads/writes go through `shardio`, everything else
dual-form through `safeio`, browser fetches through `fetch_json.js`. A second
way to open the same bytes is how one of the two becomes wrong.

**Rule 13. A guard that closes a class needs a test that reproduces the
class. Not a clean-run test — a test that plants an instance of the class
and fails if the guard passes. This test must exist before the guard is
trusted, and it must be added to COVERAGE.md alongside the guard.**

Session 19 is the evidence. The reader-usage guard first shipped line-based
and passed vacuously on a wrong scan root — proven only when a planted
`open()` and a planted `fetch()` were confirmed to fail naming the file.
The negative controls are the reason the guard is trusted, not the clean
run. Every guard from here on ships with its class-reproducing test, and
COVERAGE.md records the test next to the guard it vouches for.

**On unsigned commits.** Commits in this repository are unsigned, by policy,
not by accident: there is no signing key, and nothing in the pipeline or the
deploy verifies signatures. `GIT_SIGN_COMMITS` may be enabled in a
contributor's environment; commits made here will then report a signing
failure and land unsigned, which is the expected state. See SHIP.md.

**Rule 14. A claim in content is verified the same way a claim in code is.
If a lesson says ⲭⲱ means 'say', that claim is checked against the
dictionary the same way a function's return value is checked against a
test. Authoring without verification is the same as coding without tests.**

Session 21 is the evidence. The lesson audit found taught glosses the
dictionary does not contain (ⲭⲱ as "say" — it means "put, place"; ϭⲟⲓⲗⲉ
as "worm" — it means "dwell"), each written from memory and each wrong.
`lesson_vocab_guard.py` now checks every taught pair the way the test suite
checks every return value, and `content/GRAMMAR_CLAIMS.md` holds every
grammar assertion pending a reviewer's verdict.

**Rule 15. A template references data by explicit path, not by enumerating
a directory. If a template needs data/dist/dict/index.json, it reads that
file, not data/. If a build system enumerates a data root, isolate unrelated
file types from that root. A template that assumes data/ contains only small
files is a bug waiting for the first large file.**

Why: Session 22's E35 — referencing site.Data in a Hugo template made Hugo
unmarshal everything under data/, including corpus.tar.gz. The tarball is
not UTF-8, unmarshalling crashed the build, and the fix was to generate the
page as a standalone static file. The failure mode was a template whose data
source had a larger scope than the template assumed. The class applies to
Hugo site.Data, Jekyll site.data, Next.js getStaticProps returning a
directory, and any templating engine with an implicit data source.

The correct shape: data/dist/dict/index.json is a file; data/dist is a
directory containing files, some of which are not data for templates. A
template that wants one file names it. A template that names a directory is
asking the build system to enumerate, and the build system will enumerate
everything.

**Rule 16. A feature is shipped when it is live on the public URL and
verified there. Preview URLs, local builds, and pushes to the repository
are staging, not shipping. A push to the repository is not a deploy; a
deploy is a deploy.**

Why: Session 15 shipped production via direct `wrangler pages deploy`
because there was no git remote. Sessions 16–22 built seven major features
— quizzes, drills, course, transliterator, writing, pronunciation, Anki —
pushed to origin/master, and did not deploy. If a learner loaded the public
URL between Sessions 15 and 23, they saw the Session 15 state. Every session
reported "pushed" as if that were the finish line. It was not.

The correct shape: after every session that changes user-facing behavior,
either promote to production and run the post-deploy checklist, or state
explicitly in the receipt "not deployed; the public URL is stale." Silence
on the deployment state is not the same as "shipped."

The failure mode is subtle: the code is correct, the tests pass, the push
succeeds, and the site is old. Nothing fails. The gap is invisible until
someone checks the URL.

**Rule 17. A status code is not the existence of a route. An SPA
fallback, a CDN, or a reverse proxy can serve HTTP 200 for any path. A
route exists if and only if its response content is what only that route
could produce — the title, a marker element, a specific script include,
a distinctive string in the body, or a content-hash. A checklist that
reads status codes has verified the CDN is responding, not that the
routes exist.**

Why: Session 23 — coptic-reference.pages.dev's SPA fallback returned
HTTP 200 with the homepage for every path, including paths that don't
exist. Every route check that read status codes alone across Sessions
15-22 could not have distinguished a working route from a broken one.
The fix was to check titles (parse the <title> and compare) and content
markers (unique strings, script includes) rather than status codes. The
failure mode is silent: a site with zero broken links and one broken
route looks identical to a site with all routes working, if you only
check status.

The correct shape: a deploy checklist entry for a route is (status ==
200) AND (title matches expected) AND (marker element present). The
second and third conditions are the ones that prove the route.
